# Chapter 15. Algorithm Complexity

## 15.1 Why Estimate Complexity

One problem can be solved by different algorithms. The choice between them
cannot be made "by eye": the difference can be a factor of millions.

Example: searching an array of 1,000,000 elements.
- linear search — up to 1,000,000 comparisons;
- binary search — 20 comparisons.

Timing with a stopwatch is not enough: the result depends on
the computer, the language, the compiler. We need a **machine-independent** estimate —
how the number of operations grows as the size of the input grows.

## 15.2 Asymptotic Notation

Let T(n) be the number of elementary operations for an input of size n.

| Notation | Meaning | Formally |
|----------|---------|----------|
| **O(f)** | **upper** bound ("no worse than") | T(n) ≤ c·f(n) for n ≥ n₀ |
| **Ω(f)** | lower bound ("no better than") | T(n) ≥ c·f(n) |
| **Θ(f)** | tight bound | O(f) and Ω(f) at once |

In practice people most often say "complexity O(…)", meaning Θ.

### Simplification rules
1. **Constants are dropped:** O(3n) = O(n), O(n/2) = O(n).
2. **The leading term remains:** O(n² + n + 100) = O(n²).
3. **Consecutive sections add up:** O(n) + O(n²) = O(n²).
4. **Nested loops multiply:** O(n) · O(m) = O(n·m).
5. The base of the logarithm does not matter: O(log₂n) = O(log₁₀n) = O(log n).

## 15.3 Complexity Classes

| O | Name | n=10 | n=1 000 | n=10⁶ |
|---|------|------|---------|-------|
| O(1) | constant | 1 | 1 | 1 |
| O(log n) | logarithmic | 3 | 10 | 20 |
| O(n) | linear | 10 | 10³ | 10⁶ |
| O(n log n) | linearithmic | 33 | 10⁴ | 2·10⁷ |
| O(n²) | quadratic | 100 | 10⁶ | 10¹² |
| O(n³) | cubic | 10³ | 10⁹ | 10¹⁸ |
| O(2ⁿ) | exponential | 1024 | ∞* | ∞* |
| O(n!) | factorial | 3.6·10⁶ | ∞* | ∞* |

*\* will not finish within the lifetime of the Universe.*

### A practical rule
A modern computer performs ≈10⁸–10⁹ simple operations per second.
So in 1 second you can realistically process about:

| Complexity | Maximum n |
|------------|-----------|
| O(n!) | 10–11 |
| O(2ⁿ) | 20–25 |
| O(n³) | 300–500 |
| O(n²) | 10 000 |
| O(n log n) | 10⁶ |
| O(n) | 10⁷–10⁸ |
| O(log n) | practically any |

The table corresponds to C++ (≈10⁸–10⁹ operations per second). In Python there are usually 10–100 times fewer operations per second; in JavaScript (Node.js) it is closer to C++, but with an allowance for the JIT compiler's "warm-up".

## 15.4 How to Count Complexity

### O(1) — does not depend on n

**Python**

```python
x = a[0] + a[-1]
d = n % 10
```

**C++**

```cpp
int x = a[0] + a.back();
int d = n % 10;
```

**JavaScript**

```javascript
const x = a[0] + a.at(-1);
const d = n % 10;
```

### O(n) — a single pass

**Python**

```python
s = 0
for x in a:          # n iterations
    s += x           # O(1) each
```

**C++**

```cpp
int s = 0;
// n iterations
    // O(1) each
}
```

**JavaScript**

```javascript
let s = 0;
// n iterations
  // O(1) each
}
```

### O(n²) — nested loops over n

**Python**

```python
for i in range(n):
    for j in range(n):
        ...
```

**C++**

```cpp
for (int i = 0; i < n; ++i) {
    for (int j = 0; j < n; ++j) {
        // ...
    }
}
```

**JavaScript**

```javascript
for (let i = 0; i < n; i++) {
  for (let j = 0; j < n; j++) {
    // ...
  }
}
```

Even a "triangular" loop gives O(n²):

**Python**

```python
for i in range(n):
    for j in range(i + 1, n):      # n(n-1)/2 iterations = O(n²)
        ...
```

**C++**

```cpp
for (int i = 0; i < n; ++i) {
    // n(n-1)/2 iterations = O(n²)
        // ...
    }
}
```

**JavaScript**

```javascript
for (let i = 0; i < n; i++) {
  // n(n-1)/2 iterations = O(n²)
    // ...
  }
}
```

### O(log n) — the problem size shrinks by a factor of k each time

**Python**

```python
while n > 0:
    n //= 2            # log2(n) iterations
```

**C++**

```cpp
while (n > 0) {
    // log2(n) iterations
}
```

**JavaScript**

```javascript
while (n > 0) {
  // log2(n) iterations
}
```

### O(n log n) — log n levels, O(n) work on each
Merge sort, Timsort.

### O(2ⁿ) — two recursive calls without memoization

**Python**

```python
def fib(n):
    return n if n < 2 else fib(n-1) + fib(n-2)
```

**C++**

```cpp
long long fib(int n) {
    return n < 2 ? n : fib(n - 1) + fib(n - 2);
}
```

**JavaScript**

```javascript
function fib(n) {
  return n < 2 ? n : fib(n - 1) + fib(n - 2);
}
```

## 15.5 Hidden Complexity of Built-In Operations

The most common mistake among students is to assume that `in` or `insert` are free.

| Operation | list | dict / set |
|-----------|------|------------|
| access by index/key | O(1) | O(1) |
| `x in collection` | **O(n)** | **O(1)** |
| `append` / `add` | O(1) | O(1) |
| `insert(0, x)` | **O(n)** | — |
| `pop()` | O(1) | — |
| `pop(0)` | **O(n)** | — |
| `remove(x)` / `del d[k]` | O(n) | O(1) |
| `min` / `max` / `sum` | O(n) | O(n) |
| `sort()` | O(n log n) | — |
| slice `a[i:j]` | O(j−i) | — |
| `len` | O(1) | O(1) |

The same for the data structures of C++ and JavaScript:

| Operation | C++ `vector` | C++ `unordered_set` / `unordered_map` | C++ `set` / `map` | JS `Array` | JS `Set` / `Map` |
|----------|--------------|--------------------------------------|-------------------|------------|-----------------|
| access by index/key | O(1) | O(1) on average | O(log n) | O(1) | O(1) |
| search for an element (`x in`) | O(n) (`find`) | O(1) on average | O(log n) | O(n) (`includes`) | O(1) (`has`) |
| append / insert | O(1) amortised | O(1) on average | O(log n) | O(1) (`push`) | O(1) |
| insert at the beginning | O(n) | — | — | O(n) (`unshift`) | — |
| removing an element | O(n) | O(1) on average | O(log n) | O(n) (`splice`) | O(1) |
| sorting | O(n log n) (`sort`) | — | already ordered | O(n log n) (`sort`) | — |

### A classic optimization example

**Python**

```python
# O(n·m) — a linear search for each element
common = [x for x in a if x in b]              # b is a list

# O(n+m) — a membership check in O(1)
bset = set(b)
common = [x for x in a if x in bset]
```

**C++**

```cpp
// O(n·m) — a linear search for each element (b is a vector)
vector<int> common;
for (int x : a) {
    if (find(b.begin(), b.end(), x) != b.end()) {
        common.push_back(x);
    }
}

// O(n+m) — membership check in O(1)
unordered_set<int> bset(b.begin(), b.end());
common.clear();
for (int x : a) {
    if (bset.count(x)) {
        common.push_back(x);
    }
}
```

**JavaScript**

```javascript
// O(n·m) — a linear search for each element (b is an array)
let common = a.filter(x => b.includes(x));

// O(n+m) — membership check in O(1)
const bset = new Set(b);
common = a.filter(x => bset.has(x));
```

### String concatenation

**Python**

```python
s = ""
for ch in parts:        # O(n²): a new string each time
    s += ch

s = "".join(parts)      # O(n)
```

**C++**

```cpp
string s;
for (const string &ch : parts) {
    // amortised O(1) per append: O(n) overall, because string is mutable
}
```

**JavaScript**

```javascript
let s = "";
for (const ch of parts) {
  // modern engines optimise this, but join is more reliable for large volumes
}

const t = parts.join("");   // O(n)
```

Quadratic concatenation is specific to languages with immutable strings (Python). In C++ it appears only with `s = s + ch` (a new copy every time).

## 15.6 Complexity of Recursion

For recursion of the form T(n) = a·T(n/b) + O(nᵏ) there is the Master
theorem. Simple cases:

| Recurrence | Example | Complexity |
|------------|---------|------------|
| T(n) = T(n−1) + O(1) | factorial | O(n) |
| T(n) = T(n−1) + O(n) | selection sort | O(n²) |
| T(n) = T(n/2) + O(1) | binary search | O(log n) |
| T(n) = 2T(n/2) + O(n) | merge sort | O(n log n) |
| T(n) = 2T(n−1) + O(1) | Towers of Hanoi | O(2ⁿ) |

The **memory** of recursion = the depth of the stack:
`factorial(n)` — O(n), `merge_sort` — O(log n) of stack + O(n) of data.

## 15.7 Space Complexity

The **additional** memory (beyond the input) is estimated.

**Python**

```python
# O(1) of additional memory
def reverse_inplace(a):
    for i in range(len(a) // 2):
        a[i], a[-1-i] = a[-1-i], a[i]

# O(n) of additional memory
def reverse_copy(a):
    return a[::-1]
```

**C++**

```cpp
// O(1) extra memory
void reverse_inplace(vector<int> &a) {
    for (size_t i = 0; i < a.size() / 2; ++i) {
        swap(a[i], a[a.size() - 1 - i]);
    }
}

// O(n) extra memory
vector<int> reversed_copy(const vector<int> &a) {
    return vector<int>(a.rbegin(), a.rend());
}
```

**JavaScript**

```javascript
// O(1) extra memory
function reverseInplace(a) {
  for (let i = 0; i < Math.floor(a.length / 2); i++) {
    [a[i], a[a.length - 1 - i]] = [a[a.length - 1 - i], a[i]];
  }
}

// O(n) extra memory
function reverseCopy(a) {
  return [...a].reverse();
}
```

There is often a **time ↔ memory tradeoff** (time–space tradeoff):
memoization spends memory to save time.

## 15.8 Best, Average, and Worst Cases

| Algorithm | Best | Average | Worst |
|-----------|------|---------|-------|
| linear search | O(1) — the first element | O(n) | O(n) — absent |
| binary search | O(1) — the middle | O(log n) | O(log n) |
| insertion | O(n) — already sorted | O(n²) | O(n²) — reversed |
| quicksort | O(n log n) | O(n log n) | O(n²) |
| merge | O(n log n) | O(n log n) | O(n log n) |

For reliability, people usually focus on the **worst** case.

## 15.9 Measuring in Practice

**Python**

```python
import time

t0 = time.perf_counter()
algorithm(data)
print(f"{time.perf_counter() - t0:.4f} s")
```

**C++**

```cpp
auto t0 = chrono::steady_clock::now();
algorithm(data);
auto t1 = chrono::steady_clock::now();
cout << fixed << setprecision(4) << chrono::duration<double>(t1 - t0).count() << " s" << endl;
```

**JavaScript**

```javascript
const t0 = performance.now();
algorithm(data);
console.log(`${((performance.now() - t0) / 1000).toFixed(4)} s`);
```

In C++ use `<chrono>` (`steady_clock` is for measuring intervals), in JavaScript — `performance.now()` or `console.time()`/`console.timeEnd()`.

**Python**

```python
import timeit
timeit.timeit("sorted(a)", globals=globals(), number=1000)
```

**C++**

```cpp
auto t0 = chrono::steady_clock::now();
for (int i = 0; i < 1000; ++i) {
    vector<int> b = a;
    sort(b.begin(), b.end());
}
// seconds for 1000 repetitions
```

**JavaScript**

```javascript
console.time("sorted");
for (let i = 0; i < 1000; i++) {
  [...a].sort((x, y) => x - y);
}
// prints the time for 1000 repetitions
```

There is no ready-made `timeit` in C++ and JavaScript. In C++ with optimisations (`-O2`) the compiler may drop "useless" work whose result is not used; in JavaScript the first repetitions are slower because of the JIT "warm-up" — so many repetitions are measured and the first ones are discarded.

### Experimental check of the complexity class
We double n and see how the time changes:

| If the time… | Complexity |
|--------------|------------|
| did not change | O(1) or O(log n) |
| grew by a factor of 2 | O(n) |
| grew by a factor of ~2.2 | O(n log n) |
| grew by a factor of 4 | O(n²) |
| grew by a factor of 8 | O(n³) |

## 15.10 What Asymptotics Does NOT Tell You

- **Constants matter** for small n: an O(n²) with a small constant
  can be faster than O(n log n) when n < 50
  (this is why Timsort uses insertion sort internally).
- It does not account for the CPU cache, data locality, or memory cost.
- An O(n) with a heavy operation inside can be worse than an O(n log n)
  with a cheap one.

**Conclusion:** asymptotics is a tool for choosing an algorithm,
and the final decision is confirmed by measuring on real data.

**Three languages — different constants.** The same O(n) algorithm in C++ usually runs tens of times faster than in Python, because C++ is compiled to machine code while Python is interpreted; JavaScript (JIT compilation in Node.js) is usually in between. However, the complexity class does not depend on the language: an O(n²) algorithm in C++ for a large n will still lose to an O(n log n) algorithm in Python.
